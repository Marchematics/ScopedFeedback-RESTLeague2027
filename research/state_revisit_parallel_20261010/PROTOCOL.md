# ScopedFeedback deterministic mechanism protocol

## Scope and fixed policies

This is a Python-standard-library, in-process mechanism experiment. It performs no HTTP, network access, external downloads, release or publication. It is not the official evaluator; no official score, code-coverage improvement, unique official 5xx improvement, or SOTA result is claimed.

A, B and C use the same API fixture, entity bindings, parameter generator, baseline C/T/U/D cycle, fresh-creation identifier allocation, and shared hard physical-request budget. Only feedback policy differs:

- A: fixed baseline round robin, no feedback
- B: exact-instance, causal-state-triggered revisit
- C: B plus one deterministic local parameter variant after successful target/revisit

The parameter proposal is fixed independently of API results: state_validation proposes limit 1 → 0; the separately named synthetic_fault fixture proposes 1 → 2. Every policy within a fixture has the same components. Only C invokes their existing local-variant capability. No policy sees fixture internals or an oracle-selected winning request trace.

One feedback job may run between completed baseline turns. The baseline cursor advances only on baseline dispatches. A revisit-success variant waits for the next baseline turn. Prefix, repair, cleanup and variant success cannot recursively seed feedback. A feedback job includes at most four prefix requests, one target and one reserved repair; all physical requests count against the same cap. These fixtures require zero repairs, so their plans reserve zero. An unaffordable complete recipe is rejected before any prefix, never truncated.

## API contracts

C creates a new empty order. U adds one item. T checks state before limit: empty is 409; a ready order with item count greater than the schema-valid nonnegative limit returns 422; otherwise it returns 200. Thus T(1) observes readiness without mutation in the primary fixture. D deletes the concrete order. Changing observed_at response noise never changes causal revision. Separate consuming mode consumes the item on successful T(1).

The synthetic_fault subclass deliberately returns 500 for ready T(2). This is a planted fault for testing discovery plumbing, not evidence of a defect in an external service.

Resource identities carry full parent chain, generation, exact type, ID and auth context. This fixture issues mutation event IDs from one globally monotonic API counter across all parents and instances; nonmutation request IDs use a disjoint prefix. A real adapter must namespace resource-local event IDs with the complete resource key/generation before sending them to the scheduler. Repeated completion evidence is idempotent. Accepted 202 is pending; later completion can advance once. Representation/ETag refresh is separate from causal revision. 403 and 412 require corresponding evidence rather than arbitrary state mutations. ConstructivePrefix excludes its target, rebinds fresh producer ID/version outputs, and charges every actual replay dispatch including failure.

## Hand illustration versus real integration

The explicitly hand-specified nonconsuming illustration is C,T(1),U,T(1),T(0),D: six physical requests, statuses 201,409,200,200,422,204. It is not output from the fair scheduler.

When successful T consumes the item, that hand illustration must insert fresh C,U before its variant: eight physical requests, including both replay calls. Reusing the consumed instance does not reproduce the ready pre-target state.

The actual fair C integration does not reproduce the six-request illustration. After C,T(1),U,revisit-T(1), the required baseline D runs before the variant. At budget six, its three-request replay-plus-variant recipe is refused and C does not reach 422. At budget eight, the actual trace is C,T(1),U,revisit-T(1),D,prefix-C,prefix-U,variant-T(0), ending in 422. The separately planted-fault fixture has the same six-request negative and eight-request path, ending in planted 500. The eight-request integration has already used D on the old resource; it does not include cleanup of the newly replayed resource.

This negative is retained. We have not replaced the fixed policy with a two-target feedback job, forced an oracle trace, or relabeled a 422 as a server fault. A different bounded-burst policy would require a separate frozen protocol and equal-budget comparison.
